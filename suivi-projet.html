📋 Suivi de projet

Cette section présente les savoir-faire liés à la gestion et au suivi du projet de diffusion TV. Deux traces illustrent la collecte et l'analyse des besoins utilisateurs (cahier des charges) ainsi que la conception de l'architecture technique et l'organisation du travail avec Git. Le bilan évalue le niveau atteint dans ces savoir-faire généraux.

Description de la trace S-1

La trace S-1 est un extrait du cahier des charges officiel fourni par la Fondation Pluriel. Ce document est le point de départ de tout le projet : il liste les acteurs impliqués et recense les besoins de chaque pôle via des entretiens menés auparavant par la cheffe de projet. J'ai utilisé ce document comme base de référence tout au long du développement, pour m'assurer que chaque fonctionnalité développée répondait à un besoin réel. La complexité réside dans la diversité des besoins : chaque pôle a des exigences différentes, parfois contradictoires (ex : niveau de personnalisation vs. harmonisation centrale du service communication).

Description des savoir-faire élémentaires

Identifier les acteurs et parties prenantes : le tableau de la trace S-1 montre 9 parties prenantes avec des rôles distincts (cheffe de projet, expert métier, contributeurs métier). J'ai compris que chaque rôle implique un niveau d'implication et des attentes différents. Les contributeurs (responsables de pôle) sont les futurs utilisateurs finaux ; les chefs de projet pilotent l'avancement ; l'expert métier est mon encadrant technique direct. Cette identification des acteurs, vue en cours de gestion de projet (R3.05), m'a permis de prioriser les fonctionnalités selon les profils d'utilisateurs.

Recueillir et synthétiser les besoins métier : le tableau des besoins de la trace S-1 montre comment des besoins hétérogènes (vidéos, PowerPoint, météo, plages horaires, différenciation par site…) ont été synthétisés en fonctionnalités concrètes. Les marqueurs (1) à (4) représentent les quatre profils d'usage principaux qui ont guidé la conception de l'application. En croisant ces besoins, j'ai défini les entités clés : Présentation, Programme, Tv, PlageHoraire. Ce travail de traduction des besoins en modèle de données est un savoir-faire partiellement vu en cours (analyse/conception), renforcé ici sur un cas réel avec des utilisateurs finaux concrets.

Identifier les contraintes non-fonctionnelles : au-delà des fonctionnalités, le cahier des charges impliquait des contraintes importantes : fonctionnement sur n'importe quelle TV avec navigateur (contrainte matérielle), authentification SSO Azure AD (contrainte sécurité), administration centralisée par le service communication (contrainte organisationnelle). Ces contraintes ont directement influencé les choix d'architecture (décrit dans la trace S-2).

Description de la trace S-2

La trace S-2 présente l'architecture générale choisie pour l'outil de diffusion TV. La décision principale a été de séparer l'application en deux projets Symfony distincts : une API REST (back-end) et une interface web (front-end d'administration). Cette architecture permet de réutiliser l'API depuis d'autres clients futurs (application mobile, autres interfaces…) et d'isoler la logique métier de l'interface utilisateur. Le schéma Git montre la structure physique du code et comment le travail a été organisé par domaine fonctionnel (entités, contrôleurs, services, templates).

Description des savoir-faire élémentaires

Concevoir une architecture logicielle multi-tiers : la trace S-2 montre la décision de séparer l'API REST de l'interface web. Ce choix résulte de l'analyse des contraintes de la trace S-1 : la TV (client léger) n'accède qu'à l'API pour afficher les présentations, tandis que les administrateurs utilisent l'interface web. Le marqueur (1) montre le CallApiService, qui centralise tous les appels HTTP depuis le web vers l'API, évitant de dupliquer la logique d'accès. Ce pattern d'architecture a été vu en cours d'architecture logicielle (R4.01) et mis en pratique pour la première fois sur un projet réel.

Justifier les choix techniques par les contraintes : la sécurisation de l'API par un token partagé (X-AUTH-TOKEN, marqueur (4)) découle de la contrainte que l'API doit être inaccessible depuis l'extérieur sans authentification. Le choix de Symfony (et non d'un framework plus léger) était justifié par la maîtrise de l'équipe et la complexité du modèle de données.

Utiliser Git pour le versioning : le schéma de la trace S-2 montre la structure des deux dossiers dans le même dépôt Git. J'ai utilisé Git tout au long du stage pour versionner mes modifications, avec des commits réguliers et descriptifs. Le versioning m'a permis de revenir en arrière lors d'une régression sur la gestion des plages horaires, ce qui a été un apprentissage concret de l'utilité du contrôle de version. Git était vu en cours (R1.07 Git) mais c'est lors du stage que j'ai réellement compris son apport sur un projet professionnel de longue durée.

Organiser le travail en phases progressives : j'ai organisé mon travail en trois phases successives : (1) conception du modèle de données et mise en place de l'API, (2) développement de l'interface d'administration, (3) développement du client TV (vue affichage). Cette progression logique du fond vers la forme a permis de valider chaque couche avant d'en construire la suivante.

Savoir analyser les besoins utilisateurs et contribuer à un cahier des charges
Intermédiaire

Savoir-faire élémentaires : identifier les parties prenantes, synthétiser des besoins hétérogènes, traduire les besoins en fonctionnalités (entités métier), identifier les contraintes non-fonctionnelles (trace S-1).
Contexte d'apprentissage : partiellement vu en cours (R3.05 Gestion de projet, R3.08 Analyse). Le cahier des charges était déjà rédigé en arrivant, mais j'ai dû l'analyser, le comprendre et l'utiliser pour guider toutes mes décisions de développement.
Difficulté : moyenne — la difficulté principale était de comprendre le métier (médico-social) pour traduire les besoins en fonctionnalités logicielles pertinentes.
Avant : débutant (projets académiques avec besoins déjà définis). Après : intermédiaire — je comprends la structure d'un cahier des charges professionnel et suis capable d'en déduire un modèle de données. Je n'ai cependant pas conduit d'entretiens utilisateurs moi-même.

Savoir concevoir l'architecture d'une application et organiser son travail
Bon

Savoir-faire élémentaires : concevoir une architecture multi-tiers API/Web, organiser le code par couches (Controller, Service, Entity), utiliser Git pour le versioning, organiser le développement en phases successives (trace S-2).
Contexte d'apprentissage : l'architecture logicielle était vue en cours (R4.01) de manière théorique. La mise en pratique sur un projet réel avec une contrainte de réutilisabilité (API accessible par plusieurs clients) m'a permis de comprendre concrètement l'intérêt de la séparation des responsabilités.
Avant : intermédiaire (architecture MVC en cours, pas de API/front séparés). Après : bon — je maîtrise la conception d'une architecture bi-applicative cohérente, et j'ai développé des automatismes de structuration du code (services, repositories, injection de dépendances) qui me font gagner du temps.
