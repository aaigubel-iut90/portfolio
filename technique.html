⚙️ Technique informatique

Cette section présente les savoir-faire techniques mis en œuvre lors du développement de l'outil de diffusion TV. Trois traces illustrent des savoir-faire élémentaires liés à la conception du modèle de données, au développement d'une API REST et à l'implémentation d'une authentification Azure AD. Le bilan évalue le niveau d'expertise atteint dans les savoir-faire généraux correspondants.

Créer des entités PHP annotées (Doctrine ORM) Définir des relations entre entités (ManyToOne, OneToMany, ManyToMany) Utiliser les groupes de sérialisation Symfony Mapper un modèle objet vers une base de données relationnelle

Description de la trace T-1

La trace T-1 montre la classe d'entité Presentation de l'API Symfony (projet diffusion_tv.api). Une Présentation représente un diaporama planifié que les écrans TV afficheront selon un programme donné, sur des jours et des plages horaires définis. Elle est l'entité centrale de l'application : toute diffusion de contenu passe par la création d'une présentation, qui contient plusieurs Articles (pages à afficher) et est rattachée à un Programme (groupement de présentations suivi par un ou plusieurs écrans). Les annotations #[Groups] contrôlent quels champs sont exposés dans les réponses JSON de l'API, selon le contexte de sérialisation.

Description des savoir-faire élémentaires

Créer des entités PHP annotées avec Doctrine ORM : la trace T-1 illustre comment j'ai déclaré chaque attribut de l'entité via des attributs PHP natifs (#[ORM\Column], #[ORM\Id]…). J'ai utilisé ce savoir-faire pour l'ensemble des entités du projet : Presentation, Article, Programme, Tv, User, PlageHoraire et ProgrammeSite. Ce savoir-faire, vu en cours de développement web à l'IUT, a été approfondi en consultant la documentation Symfony/Doctrine et en l'appliquant à un modèle métier réel.

Définir des relations entre entités : les marqueurs (3), (4) et (5) de la trace T-1 montrent les trois types de relations utilisés dans le projet. La relation ManyToOne vers Programme traduit qu'une présentation appartient à un programme. La relation OneToMany vers Article traduit qu'une présentation est composée de plusieurs pages. J'ai dû comprendre la notion de côté propriétaire (owning side) pour éviter les erreurs de persistance, ce qui n'avait été qu'effleuré en cours.

Utiliser les groupes de sérialisation Symfony : le marqueur (2) montre l'annotation #[Groups(['presentation:read'])]. J'ai utilisé ce mécanisme pour contrôler finement quels champs sont sérialisés dans les réponses JSON, évitant ainsi les références circulaires (par exemple, ne pas inclure l'intégralité de l'objet User dans chaque présentation). Ce savoir-faire était nouveau pour moi et a été appris entièrement lors du stage.

Description de la trace T-2

La trace T-2 montre un extrait du PresentationController de l'API, qui expose les opérations CRUD sur la ressource Presentation. Ce contrôleur est typique de l'architecture de l'API : chaque ressource (Tv, Programme, Article…) dispose d'un contrôleur dédié avec ses cinq endpoints standard (GET all, GET one, POST, PUT, DELETE). Ce contrôleur est appelé par le front-end web via le service CallApiService à chaque fois qu'un administrateur crée ou modifie une présentation dans l'interface.

Description des savoir-faire élémentaires

Implémenter les endpoints CRUD d'une ressource REST : les marqueurs (1) et (2) de la trace T-2 montrent comment j'ai déclaré les routes avec les méthodes HTTP appropriées (GET, POST, PUT, DELETE). J'ai implémenté ce pattern pour toutes les entités du projet. La conception "resource-oriented" de l'API (une URL pour une ressource, un verbe HTTP pour l'action) était vue sommairement en cours ; c'est lors du stage que j'ai vraiment compris et appliqué les conventions REST.

Retourner des réponses JSON typées : le marqueur (5) montre le retour d'un JsonResponse avec le code HTTP 201 (Created) et le groupe de sérialisation approprié. J'ai veillé à utiliser les codes HTTP sémantiquement corrects (200, 201, 204, 404…) pour chaque opération. La gestion cohérente des codes de retour est un savoir-faire que j'ai entièrement développé lors du stage.

Persister des données via l'EntityManager : les marqueurs (4) montrent la séquence persist() / flush() de Doctrine, nécessaire pour enregistrer les données en base. J'ai appris à distinguer l'opération de persistance (marquer l'entité comme à sauvegarder) du flush (déclencher réellement les requêtes SQL), ce qui m'a permis d'optimiser certaines opérations en lot (ex : suppression en cascade des articles d'une présentation).

Description de la trace T-3

La trace T-3 montre le cœur du système d'authentification de l'interface web. L'application ne gère pas ses propres mots de passe : les utilisateurs se connectent via leur compte Microsoft Azure Active Directory (SSO de la Fondation), ce qui garantit la cohérence avec le système d'information existant. Cette trace est placée dans le cadre du sujet car l'accès sécurisé à l'outil est une contrainte non-fonctionnelle essentielle : sans elle, n'importe qui pourrait modifier les diffusions sur les écrans.

Description des savoir-faire élémentaires

Implémenter un Authenticator Symfony personnalisé : le marqueur (1) montre que j'ai créé une classe implémentant l'interface AbstractAuthenticator de Symfony Security. J'ai dû comprendre le cycle de vie de l'authentification Symfony (méthodes supports(), authenticate(), onAuthenticationSuccess()), un concept que je n'avais jamais rencontré en cours. Ce savoir-faire a été entièrement appris lors du stage, en s'appuyant sur la documentation officielle Symfony.

Intégrer OAuth2 avec Azure AD : les marqueurs (2) et (3) de la trace T-3 montrent la gestion du double contexte (développement vs. production) et l'utilisation du bundle KnpOAuth2ClientBundle pour récupérer le token Azure. J'ai dû comprendre le flux Authorization Code d'OAuth2, configurer les redirections et gérer les données retournées par l'API Microsoft Graph pour extraire le profil utilisateur. C'est le savoir-faire le plus avancé de ce stage, découvert et maîtrisé entièrement en autonomie.

Gérer les rôles dynamiquement depuis l'API : les marqueurs (4) et (5) montrent une décision architecturale importante : les rôles (ROLE_ADMIN, ROLE_SUPER_ADMIN…) ne sont pas stockés dans Azure AD mais dans la base de données de l'API. Ainsi, un administrateur peut changer les droits d'un utilisateur sans intervention sur Azure, simplement depuis l'interface.

📊 Bilan & Analyse — Savoir-faire généraux techniques

Les trois traces précédentes illustrent des savoir-faire élémentaires associés à trois savoir-faire généraux. Voici une évaluation justifiée de mon niveau d'expertise pour chacun, en comparant avant et après le stage.

Savoir développer une API REST avec Symfony
Bon

Savoir-faire élémentaires : définir des routes REST avec les verbes HTTP, implémenter des opérations CRUD via les contrôleurs, retourner des réponses JSON avec les codes HTTP appropriés, documenter avec OpenAPI (traces T-1, T-2).
Contexte d'apprentissage : vu partiellement en cours (R3.01 Web, R4.01 Archi) sur des projets académiques sans vraie API REST. Approfondi et maîtrisé lors du stage sur un projet réel multi-entités.
Avant le stage : débutant (projets web simples sans REST). Après : bon — je suis autonome pour concevoir et implémenter une API REST complète, bien que je doive encore progresser sur les aspects sécurité avancée et pagination.

Savoir concevoir un modèle de données objet-relationnel (ORM)
Bon

Savoir-faire élémentaires : créer des entités Doctrine avec annotations PHP, définir les relations (ManyToOne, OneToMany, ManyToMany), utiliser les groupes de sérialisation, générer et appliquer des migrations (trace T-1).
Contexte d'apprentissage : les relations entre tables étaient vues en BDD SQL en cours (R2.06), mais le mapping objet-relationnel via Doctrine était nouveau. Appris lors du stage avec la documentation Doctrine et des exemples.
Avant : intermédiaire (connaissais SQL, pas l'ORM). Après : bon — je maîtrise la conception d'un modèle Doctrine pour un contexte métier réel, y compris les relations bidirectionnelles.

Savoir implémenter une authentification OAuth2 / SSO dans une application web
Intermédiaire

Savoir-faire élémentaires : implémenter un Authenticator Symfony, intégrer OAuth2/OpenID Connect via Azure AD, gérer des rôles dynamiques depuis une base de données (trace T-3).
Contexte d'apprentissage : sujet jamais abordé en cours, entièrement découvert lors du stage. L'intégration Azure AD impliquait de comprendre le protocole OAuth2, les tokens JWT et l'API Microsoft Graph.
Difficulté : élevée (nouveauté totale, peu d'exemples concrets disponibles).
Avant : débutant (authentification classique login/mdp seulement). Après : intermédiaire — je comprends et j'ai implémenté le flux complet OAuth2 avec Azure, mais des aspects comme le refresh token ou l'utilisation de JWT restent à approfondir.
